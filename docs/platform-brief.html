Guiding principles

Modular monolith first

Extract services only when scale demands. Exceptions centralized day one: identity/SSO & the control plane.

The wallet is the product

Money correctness under concurrency is the hardest, most valuable part.

One engine, two interfaces

Dashboard & API are thin clients over the same services.

Multi‑tenant from line one

Every business row carries tenant_id; RLS backstop.

Idempotent & observable

Every money/PII write is idempotent & traceable.

Three planes, not one

Control plane is never in the data plane's hot path.

Tenancy model hard to reverse

Shared DB, shared schema, tenant_id on every row, with Postgres Row‑Level Security as the backstop — cheap, easy cross‑tenant billing/analytics. A dedicated single‑tenant deployment is the escape hatch for regulated clients.

Dependency rule: products → platform (never reverse). Control‑plane governs but is read at runtime via cached config — never in the hot path.

The wallet & double‑entry ledger crown jewel

  • Balance is a derived projection of an append‑only ledger — never a mutable counter.
  • Reserve → commit / refund lifecycle; idempotency keys; FOR UPDATE concurrency.
  • Money in bigint minor units; CI invariant: Σcredits − Σdebits = balance.
  • Multi‑currency machinery; enabled set is control‑plane config; FX deferred.

Identity & SSO

One login for all apps — centralized day one because SSO can't be retrofitted.

Decision — WorkOS AuthKit (managed). Self‑serve sign‑up · hosted login · MFA mandatory for admin/owner. Chosen over Auth0 on cost at scale + B2B/enterprise‑SSO fit.

How “one for all” works

Every app is an OIDC client of one WorkOS environment sharing one user pool. A second app redirects to the same session → silent SSO, no re‑login. Tokens stay server‑side in the BFF; the browser gets only an httpOnly cookie (no JWT in JS → no XSS token theft).

Staff identity — separate from customers

  • Dedicated staff org; MFA mandatory for all staff.
  • Admin RBAC: super_admin · platform_ops · finance · support · compliance · read_only.
  • Step‑up auth + maker‑checker for money/destructive actions; time‑boxed, audited impersonation.

Two auth modes: humans → SSO; developer integrations → sk_live_/sk_test_ API keys.

Integrations — the vendor plugin framework

Vendor‑agnostic. Share the mechanism (registry · selection · failover · health), not the contract.

Plugin type vs instance

A plugin type = the adapter code (“Hubtel SMS”). A plugin instance = a configured, credentialed activation. Enable/disable, default + fallback, and bring‑your‑own‑credentials all operate on instances. Adding a vendor = ship a type + create an instance. Zero core changes.

The app never calls a vendor directly — sends & top‑ups go through platform/integrations; only the provider plugin adapter makes the outbound call. That indirection is what enables failover, no‑lock‑in, and per‑provider billing.

Treating payments like SMS would double‑charge customers — so failover policy is per‑capability.

Honest billing model

Each provider declares a billable‑status set + a platform‑fault exemption list. Bill the customer on the same basis the provider bills us; never charge for failures the platform caused (internal error, suspension, fraud/geo block → auto‑refund). Always show reconciled DLR + cost‑per‑delivered.

Strategic endgame

At volume, our own SMS gateway / payment rails become just new platform‑scoped plugin instances — a migration, not a rewrite (canary via routing weights; keep vendors as fallback).

Control Plane (Admin)

The privileged system that configures, monitors & governs every product — current and future.

Core rule: the control plane configures & observes the data plane but is never in its hot path. The data plane reads cached last‑known‑good config and keeps serving if admin is down.

Four jobs

Configure

provider instances · routing · pricing · feature flags · rate limits · enabled currencies · product registry

Monitor

health · SLOs · usage/spend · fraud · ledger invariant · DLR‑trust · revenue

Govern

tenant lifecycle · sender‑ID approvals · KYC/compliance · DSR/erasure · sub‑processor list

Operate

kill‑switches · impersonation · money ops (maker‑checker) · breach response · replay

Future products plug in

Each product registers a ProductManifest (config schema · metrics · health · admin actions) → instantly configurable/monitorable with zero console changes — the same “share the mechanism” pattern as vendor plugins, one level up.

Compliance & Data Protection

GDPR‑grade baseline (the African laws mirror it). Researched vs Twilio / Infobip / Bird + Ghana DPA / Nigeria NDPA.

Controller vs Processor

DataOur role & duties
Tenants' recipients' data (phone, body, contacts)Processor — offer DPA, disclose sub‑processors, assist DSRs
Tenant users + billing dataController — lawful basis, retention, honor DSRs

PII tokenization & erasure schema‑shaping

  • Raw PII lives only in an encrypted pii_vault (per‑subject DEK, envelope‑encrypted in KMS).
  • Everything else references a stable subject_id surrogate — never a raw phone column.
  • Right‑to‑erasure = crypto‑shred the DEK → PII unreadable in one op; ledger/audit rows stay intact.

Data residency re‑scoped per research

Residency is per‑data‑class, not per‑tenant. Only BVN/NIN/NIBSS & domestic card‑switching are legally in‑country — we don't ingest those, so our data needs only NDPA safeguards (Transfer Impact Assessment + SCCs + consent), hosted in AWS Cape Town. Per‑data‑class hybrid is the real‑world model (Moniepoint).

Enforcement is real: MultiChoice fined ₦766m for unconsented cross‑border transfer. Consent + lawful‑basis design at onboarding is the priority.
Differentiator: African rivals largely lack ISO 27001 / SOC 2. We design to be certifiable and adopt Bird‑style DSR‑by‑API — compliance as a selling point, not just a cost.

Hardening highlights

  • Redis: dedicated node‑based queue (noeviction+AOF+Multi‑AZ) — not ElastiCache Serverless; separate cache.
  • Idempotent payment consumers (at‑least‑once + stalled jobs = duplicates).
  • Fargate subnets /20+ (no ENI trunking caps autoscaling); PID‑1/tini SIGTERM draining.
  • RLS: app uses a non‑owner role (owner bypasses RLS); tenant_id leading index; pgTAP cross‑tenant tests gate CI.
  • Migrations: expand‑contract + lock_timeout + advisory lock + CREATE INDEX CONCURRENTLY.
  • Config ≠ deploy; blue/green; CI→AWS via GitHub OIDC; break‑glass prod access (certifiability).
