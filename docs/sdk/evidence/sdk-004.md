# SDK-004 generate and verify typed definition catalogs — evidence

> Status: implementation complete, **release item NOT closed** — 2026-07-18. Code shipped in
> `dbfd7d1` (PR #144) alongside SDK-003 slice 6b; this document is the retrospective completion
> audit that should have accompanied it. One acceptance clause (AC02 channel) remains open and
> requires a release-owner decision — see "Open before closure".

## Outcome

`@fabric-messaging/cli` (binary `fabric`) generates a deterministic, type-safe managed-message
catalog for exactly one application environment from a least-privilege `definitions:read` key, and
verifies it against live contracts in CI. Generated output contains no key, message content,
sender/provider identifier, or recipient data. The typed `Fabric<Catalog>` client turns a released
definition's stable key and variable schema into compile-time errors at the call site, while the
same invalid payloads are rejected at runtime by the server-side validator that preview and send
already share.

## Acceptance traceability

| Criterion | Evidence |
| --- | --- |
| SDK-004-AC01 (generate twice, no contract change → byte-identical) | `packages/cli/src/generate.spec.ts` "emits deterministic exact TypeScript without operational identifiers": `generateCatalog(manifest())` run twice asserts `first === second`, and asserts the output contains none of the application/environment UUIDs, `sender`, `provider`, or `body`. |
| SDK-004-AC02 (compile-time key, required data, inline extra fields, channel, locale) | **Partial.** `packages/sdk/src/catalog.type-test.ts` proves four of five clauses with `@ts-expect-error` fixtures: unknown stable key, omitted required variable, inline extra variable, and out-of-release locale. **Channel is not constrained by any type** — see "Open before closure". |
| SDK-004-AC03 (data widened through JavaScript → same fields rejected at runtime) | The generated types narrow only the call site; the server re-validates every payload through the one `@app/domain` `validatePayload` used by preview and send. Covered by SDK-003 evidence: `message-render` unit tests (path-coded errors, value never echoed) and `message-preview.integration` (invalid payload ⇒ bounded field-path errors, no side effects). |
| SDK-004-AC04 (newer unsupported manifest → upgrade guidance, never emits `any`) | `generate.spec.ts` proves both directions: `parseManifest({manifest_version: 2})` throws `/newer @fabric-messaging\/cli/`, and a manifest demanding `minimum_sdk_contract_version: 2` throws `/Upgrade @fabric-messaging\/sdk/`. Generation is refused before any file is written, so no `any`-typed catalog can be emitted. |
| SDK-004-AC05 (send-only key denied the catalog; definitions-read key cannot send/publish/retrieve content) | Both directions now proven. Forward: `definition-catalog.controller.spec.ts` — a `sms:send` key gets `insufficient_scope`, and an unscoped dashboard token (`*`, null app/env) gets `scoped_api_key_required`. Reverse: `api-key.guard.spec.ts` "denies a definitions:read key every send, publish, and content scope" iterates the closed `apiKeyScopeValues` catalog and asserts `insufficient_scope` for every scope except `definitions:read` — a newly added scope fails this test until deliberately considered. |
| SDK-004-AC06 (sandbox/live mismatch → identifies environment, exits non-zero, no secret material) | `packages/cli/src/commands.spec.ts`: a live catalog fetched by a sandbox key throws `/environment mismatch/`; missing generated output throws `/drift detected for sandbox/` and the thrown message is asserted not to contain the key. `packages/cli/src/bin.ts` additionally redacts `sk_(test|live)_…` from stderr on every failure path and sets `process.exitCode = 1`. |

### Dashboard command-accuracy check — defect found and fixed

The required verification includes "dashboard command accuracy check against the packed CLI". The
shipped `definition-developer-setup.spec.ts` compared `DEFINITION_COMMANDS` to string literals
copied from the same module — a tautology that would survive renaming the binary, the package, or
either subcommand. It has been rewritten to read `packages/cli/package.json` and
`packages/cli/src/bin.ts` and assert the displayed commands against the CLI's declared package name,
its `bin` key, and the subcommand pair the entry point actually accepts.

## Open before closure

**AC02 channel clause is unimplemented, not merely untested.** `DefinitionContract.channels` is
declared in `packages/sdk/src/catalog.ts` but consumed by no type: `CatalogPreviewOptions` narrows
only `data` and `locale`, and neither `PreviewMessageOptions` nor `SendMessageOptions` exposes a
`channel` field at all. Today SMS is the only executable managed channel and `UngeneratedCatalog`
pins `channels: "sms"`, so no caller can currently select a wrong channel.

Under this backlog's no-waiver rule, that is not enough to close the item. The release owner must
either implement the constraint or record why the underlying risk does not exist, with the named
reviewer. Deferring it to SDK-007/SDK-008 (where a second channel first becomes selectable) is a
defensible disposition, but it must be recorded as a reviewed non-applicability rather than left
implicit.

## What is intentionally not in this increment

- Live-environment catalogs: `definitions check` distinguishes sandbox from live, but live releases
  are still refused upstream by SDK-003 (publish targets sandbox only).
- Public npm publication of `@fabric-messaging/cli` — see the external gate below.

## External gate

`@fabric-messaging/cli@0.1.0-beta.1` has **not** been published to npm; `release:check` and
`pack --dry-run` prove it is publishable, not published. Publication is a redline requiring explicit
human authorization, and is tracked alongside the pending `@fabric-messaging/sdk@beta.5` publish.
ADR-0005 also remains `proposed` — product + security sign-off is still outstanding for the
definitions work this item builds on.
