## Outcome

`@fabric-messaging/cli` (binary `fabric`) generates a deterministic, type-safe managed-message
catalog for exactly one application environment from a least-privilege `definitions:read` key, and
verifies it against live contracts in CI. Generated output contains no key, message content,
sender/provider identifier, or recipient data. The typed `Fabric<Catalog>` client turns a released
definition's stable key and variable schema into compile-time errors at the call site, while the
same invalid payloads are rejected at runtime by the server-side validator that preview and send
already share.

### Dashboard command-accuracy check — defect found and fixed

The required verification includes "dashboard command accuracy check against the packed CLI". The
shipped `definition-developer-setup.spec.ts` compared `DEFINITION_COMMANDS` to string literals
copied from the same module — a tautology that would survive renaming the binary, the package, or
either subcommand. It has been rewritten to read `packages/cli/package.json` and
`packages/cli/src/bin.ts` and assert the displayed commands against the CLI's declared package name,
its `bin` key, and the subcommand pair the entry point actually accepts.

## AC02 channel clause — deferred 2026-07-21, IMPLEMENTED in SDK-007 slice 5 (2026-07-23)

**Resolution: IMPLEMENTED.** Managed Email (SDK-007) made a second channel selectable, so the
deferral's precondition ended and the constraint was built: `CatalogPreviewOptions` gains a `channel`
narrowed to `Catalog["messages"][Key]["channels"]`, the generator + manifest + API catalog emit the
real per-definition channel, and `catalog.type-test.ts` proves with `@ts-expect-error` that a
channel-unsupported call fails to compile. The API validates a supplied channel against the released
definition (400 `channel_mismatch`) as the runtime backstop. See `docs/sdk/evidence/sdk-007.md` AC04.

**Original disposition (2026-07-21): not applicable at SDK-004; deferred to the release item that
first makes a second channel selectable (SDK-007 / SDK-008). Reviewer: product owner, 2026-07-21.**

Facts. `DefinitionContract.channels` is declared in `packages/sdk/src/catalog.ts` but consumed by no
type: `CatalogPreviewOptions` narrows only `data` and `locale`, and neither `PreviewMessageOptions`
nor `SendMessageOptions` exposes a `channel` field. So the AC02 clause "channel … checked at compile
time" is unimplemented, not merely untested.

Why the underlying risk does not exist today. AC02's purpose is to stop a developer issuing a
compile-valid call against a channel a released definition does not support. SMS is the only
executable managed channel: `UngeneratedCatalog` pins `channels: "sms"`, the generator emits
`channels: "sms"` for every definition, and the send/preview APIs have no channel parameter to
misuse. There is no reachable state in which a caller selects a wrong or unsupported channel, so the
constraint would guard against nothing until a second channel ships. Runtime safety is unaffected
regardless — the API re-validates every payload (AC03), so this is purely about compile-time
ergonomics.

Conditions attached to the deferral (make this reviewable rather than a silent waiver):
- SDK-007 and SDK-008 **cannot** close while adding a second channel unless they also land the
  `channel` narrowing in `CatalogPreviewOptions` (or its send equivalent) plus a `@ts-expect-error`
  fixture proving a channel-unsupported call fails to compile. The clause moves to that item's
  traceability; it is not dropped.
- Until then `DefinitionContract.channels` stays in the generated catalog (the data is correct and
  forward-compatible); only the *type-level enforcement* is deferred.

This satisfies the backlog's no-waiver rule: the criterion is neither silently skipped nor closed on
absent evidence — its risk is recorded as non-existent under the current single-channel surface, with
a named reviewer and an explicit re-activation trigger.
