# SDK-005 send and observe managed SMS in sandbox — evidence

> Status: in-progress local increment — persistence boundary + SDK surface verified, no push or
> external publication — 2026-07-17. Builds on SDK-003 (definitions) and SDK-002 (webhooks);
> ADR-0005 remains `proposed` (product+security sign-off required before anything leaves local).

## Outcome so far

A developer sends a released definition by stable key: `POST /v1/message-deliveries` (SDK
`fabric.messages.send`) renders through the same engine as preview, reserves sandbox funds, and
atomically persists one **delivery + attempt + message + acceptance outbox event** under a required
`Idempotency-Key`. The delivery id is **deterministic** per tenant/application/environment/key, so a
replay — including a concurrent race — returns the same resource with zero duplicate effects. The
shared transition core reconciles the message outcome back onto the attempt and delivery
(status, exact cost, `resource_version` bump), and `GET /v1/message-deliveries/:id`
(SDK `messages.retrieveDelivery`) reads it back with attempt history.

## Engineering notes

- `expiresAt` must bind as `toISOString()::timestamptz` — the tenant-tx serializer rejects `Date`
  instances (was a 500 on every managed send).
- Retention is SHIPPED end-to-end: `expires_at` + `legal_hold` + partial index
  `idx_message_deliveries_retention`, purged by a daily maintenance cron
  (`maintenance-retention.ts`, advisory-locked, provisioner connection) — capability AND trigger,
  per the "ship the trigger" rule.
- SDK parser (`message-delivery.ts`) is proven against the canonical `@app/contracts`
  `sendManagedMessageResponse` schema (round-trip in `messages.spec.ts`).
