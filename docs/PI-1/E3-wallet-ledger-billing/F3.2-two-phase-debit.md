# F3.2 — Two-phase debit (reserve → commit / refund)

**Epic:** E3 Wallet · **Priority:** MUST · **Iteration:** 2
**Depends on:** F3.1, F1.3 · **Blocks:** F5.2 send pipeline

## Why
A send isn't "subtract then send" — funds must be **reserved**, then finalized by the real outcome,
correctly under concurrency and retries.

## Stories
- **US-3.2.1** — As a **tenant**, concurrent sends can never spend the same balance twice, so I'm never over-drawn or double-charged.
- **US-3.2.2** — As a **developer**, a retried send with the same idempotency key debits **once**, so network retries are safe.

## Acceptance criteria
- [ ] `reserve(cost, idem_key)` creates a **pending debit** atomically using `SELECT … FOR UPDATE` (or version check); rejects if insufficient balance (→ `402`).
- [ ] `commit(txn)` posts the charge; `refund(txn)` reverses with a compensating entry.
- [ ] Reservation is **idempotent** on `idem_key` (F1.3) — a duplicate reserve returns the original.
- [ ] Two concurrent sends against a balance that funds only one → exactly one succeeds.
- [ ] Outcome wiring: platform-fault failure → refund; billable status → commit (per F3.5).
- [ ] **Rounding policy:** all amounts are integer **minor units**; segment-cost rounding is defined and applied consistently (no fractional drift).
- [ ] **Transactional projection (S5):** `wallets.balance_minor` is updated **in the same transaction** as every ledger posting (reserve/commit/refund/topup/reversal) — never via async outbox. So the `reserve` gate `balance_minor >= cost` always reads a consistent balance.
- [ ] **Negative balance:** reserve rejects at insufficient funds. Balance can only go negative via reversal clawback (F4.3); because the projection is transactional, **`balance_minor < 0` naturally blocks new sends** — no separate "blocked" flag (S5).
- [ ] Commit/refund use the **shared resolution state machine** (B6, see F5.4) — compare-and-set on the message/reservation row so a retry or a sweeper can't double-apply.
- [ ] Test: concurrency (N parallel reserves), retry-dedupe, insufficient-funds, rounding consistency, **negative-balance blocks send**.

## Design notes
- Pending→posted lifecycle from F3.1; commit/refund timing driven by F3.5 (billable-status set).
- Unresolved reservations are swept by F3.3; resolution guard is shared (B6).

## Out of scope (this PI)
- Partial reservations / holds across multiple products.

## Definition of Done
- Concurrency + idempotency tests green; invariant holds under a parallel-send load test.
