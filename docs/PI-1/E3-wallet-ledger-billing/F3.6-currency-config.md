# F3.6 — Enabled-currency configuration

**Epic:** E3 Wallet · **Priority:** MUST · **Iteration:** 2
**Depends on:** F3.1, F9.1 · **Blocks:** F3.4 rating, F4.2 top-up

## Why
Currency support is **configuration, not code** — fits the control-plane model and avoids a future
migration. Launch enables one currency; more are a config change.

## Stories
- **US-3.6.1** — As an **operator**, I can set the supported currencies + default in the admin console, so launching a new market is a config change, not a deploy.
- **US-3.6.2** — As a **tenant**, I can only create wallets / be priced in enabled currencies, so the system stays consistent.

## Acceptance criteria
- [ ] **Supported currencies + default** stored as control-plane config (validated ISO-4217).
- [ ] Wallet creation, pricing (F3.4), and top-ups (F4.2) **validate** against the enabled set.
- [ ] Enabling a new currency requires **no migration / no deploy** (config change only).
- [ ] Optional per-tenant narrowing via entitlement.
- [ ] Test: a disabled currency is rejected for wallet/pricing/top-up; enabling it (config) makes it work.

## Design notes
- Authored in F9.1; the multi-currency schema (F3.1) already supports N currencies — this gates the active set.

## Out of scope (this PI)
- FX between currencies.

## Definition of Done
- Config-gated currency tests; default applied on tenant onboarding.
