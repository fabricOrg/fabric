# F3.3 — Reservation-TTL sweeper

**Epic:** E3 Wallet · **Priority:** MUST · **Iteration:** 2
**Depends on:** F3.2 · **Blocks:** —

## Why
On an ambiguous send (timeout, no DLR ever arrives) a reservation could hold a customer's funds
**forever**. A sweeper guarantees funds are always eventually freed or charged. (Review gap C4.)

## Stories
- **US-3.3.1** — As a **tenant**, if a message's outcome never resolves, my reserved funds are automatically released after a bounded time, so my money is never silently locked.

## Acceptance criteria
- [ ] Each reservation has a **TTL** (default **60 min**, configurable per route; chosen > typical provider DLR latency in-region — S4). A scheduled sweeper resolves reservations still in `reserved` past TTL.
- [ ] **Same resolution state machine + `SELECT … FOR UPDATE` compare-and-set as F5.4 (B6):** the sweeper transitions `reserved → refunded` only if still `reserved`; if a DLR already resolved it, the sweep is a no-op. DLR and sweeper share the lock → never both resolve.
- [ ] Default resolution = **refund** (configurable); every sweep action is **audited** (F1.4).
- [ ] **Terminal is terminal:** once swept to `refunded`, a later DLR does not flip it (matches F5.4 S4 decision).
- [ ] Metric: count/age of open reservations; alert if backlog grows.
- [ ] Test: a reservation with a suppressed DLR is refunded after TTL; **concurrent sweeper + DLR resolves exactly once**; late DLR after sweep is a no-op.

## Design notes
- Default to refund (customer-friendly + safe); operators can tune TTL per route via config.
- The resolution state machine is **owned jointly** with F5.4 and F5.2 (B6) — implement once, used by all three.

## Out of scope (this PI)
- Per-message dynamic TTL based on route latency profiles.

## Definition of Done
- TTL sweep test + late-DLR idempotency test; open-reservation metric emitted.
