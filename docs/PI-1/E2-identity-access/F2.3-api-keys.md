# F2.3 — API keys (live/test + scopes)

**Epic:** E2 Identity · **Priority:** MUST · **Iteration:** 2
**Depends on:** F2.1 · **Blocks:** F8.* public API, F8.5 test mode

## Why
Developers' server-to-server auth. Prefix-encoded environment (Stripe) + privilege scoping (Twilio)
gives instant recognition and capped blast radius.

## Stories
- **US-2.3.1** — As a **developer**, I can mint `sk_live_` and `sk_test_` keys, so I can separate production from testing at a glance.
- **US-2.3.2** — As a **developer**, I can scope a key to specific permissions (e.g. `sms:send`, `wallet:read`), so a leaked key has limited blast radius.
- **US-2.3.3** — As a **tenant admin**, I can revoke a single key without disrupting others.

## Acceptance criteria
- [ ] Keys carry an **environment prefix** (`sk_live_…` / `sk_test_…`) and **per-resource scopes**.
- [ ] Secret shown **once** at creation; stored **hashed at rest** (Argon2/bcrypt or HMAC-pepper), prefix-indexed for lookup.
- [ ] Keys are individually **revocable**; `last_used_at` tracked.
- [ ] Requests authenticate via `Authorization: Bearer sk_…`; scope is enforced per endpoint.
- [ ] `sk_test_` keys route to **test mode** (F8.5) — never charge or hit a real carrier.
- [ ] Hook point for **secret-scanner auto-revocation** of leaked live keys.

## Design notes
- Distinct from human SSO (F2.1): keys = machine auth; both resolve to `tenant_id` + scopes.
- Rotation-with-overlap window is **PI-2** (F2.4).

## Out of scope (this PI)
- Dashboard key-rotation overlap window; restricted publishable client keys.

## Definition of Done
- Scope-enforcement test; hash-at-rest verified (no plaintext key in DB); test-key isolation test.
