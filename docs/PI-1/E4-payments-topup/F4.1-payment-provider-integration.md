# F4.1 — Payment provider integration (thin interface)

**Epic:** E4 Payments · **Priority:** MUST · **Iteration:** 4
**Depends on:** F3.1 · **Blocks:** F4.2

## Why
Tenants fund wallets to send. In-market, **mobile money + card with instant crediting** is
table-stakes (Hubtel/Paystack/Flutterwave). One provider, behind a thin interface (the generic
payment plugin framework is deferred).

## Stories
- **US-4.1.1** — As a **tenant**, I can pay via mobile money or card, so I can fund my wallet the way I actually pay.
- **US-4.1.2** — As the **platform**, the payment vendor sits behind a thin `PaymentProvider` interface, so we can swap/add providers later without touching the wallet.

## Acceptance criteria
- [ ] A `PaymentProvider` interface: `initCharge(intent) → checkout session/URL`, `parseEvent(payload) → canonical event`, `verifyWebhook(req)`, `refund(ref, amount)`.
- [ ] One concrete adapter (the launch provider) implements it; **mobile money + card** supported.
- [ ] Credentials in secrets manager; provider config validated.
- [ ] Canonical payment event model so the wallet never sees vendor-specific shapes.
- [ ] Test (sandbox): initiate a charge → receive a canonical succeeded/failed event.

## Design notes
- Thin interface now; **generic payment plugin framework + initiation-time failover = PI-2** (one provider at launch).
- Provider choice gated on launch-market decision.

## Out of scope (this PI)
- Multiple payment providers; routing/failover between them.

## Definition of Done
- Sandbox charge round-trip; canonical event mapping tested.
