# F4.2 — Top-up flow (verify-on-server)

**Epic:** E4 Payments · **Priority:** MUST · **Iteration:** 4
**Depends on:** F4.1, F3.1, F1.3 · **Blocks:** funded sends

## Why
The wallet must only be credited for **verified** money. Paystack & Flutterwave both state it
explicitly: **never trust the browser redirect; verify server-side; the webhook is the source of truth.**

## Stories
- **US-4.2.1** — As a **tenant**, after I pay I see my wallet credited reliably, even if my browser closes mid-redirect.
- **US-4.2.2** — As the **platform**, a duplicated/replayed payment callback credits the wallet **once**.

## Acceptance criteria
- [ ] Flow: `createTopup(pending)` → `initCharge` → redirect to hosted checkout → return to callback.
- [ ] **Only the webhook credits the wallet (B8).** The browser-redirect callback only **reads/polls** status for UX — it never posts a credit. This removes the callback-vs-webhook double-credit race.
- [ ] **Double-credit is prevented by a DB constraint, not an app-level check (B8):** a `UNIQUE` constraint on `ledger_transactions.idempotency_key` (derived deterministically from `topup_id`); the credit is an **insert that dedupes on conflict**, never a read-then-write.
- [ ] The provider **webhook is the source of truth**; handler verifies signature, is idempotent, returns 200 fast; retries credit once (via the unique constraint).
- [ ] Successful verification posts a `topup` **credit** to the ledger (F3.1); the matching-currency wallet is **auto-provisioned if absent** (N5); top-up currency must be enabled (F3.6).
- [ ] Test: browser-redirect-without-webhook does **not** credit; **concurrent callback + webhook credits once**; duplicate webhook credits once; signature-invalid rejected.

## Design notes
- Webhook-only credit + unique constraint is the B8 resolution (was: "verify on both callback and webhook," which had a TOCTOU double-credit window).
- Reversal/chargeback clawback + pending-sweeper are in F4.3.
- Mobile money instant-credit path supported (F4.1).

## Out of scope (this PI)
- Auto-recharge; saved payment methods.
- **Surface note:** PI-1 has **no business dashboard** (PI-2) — top-up is initiated via the **public API + dev portal**; a non-technical self-serve top-up UI lands with the dashboard in PI-2.

## Definition of Done
- E2E sandbox top-up credits the wallet once; idempotency + signature tests green.
