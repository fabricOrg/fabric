# F7.6 — Governance (DPA, consent, data residency)

**Epic:** E7 Compliance · **Priority:** MUST · **Iteration:** 1 (+ admin enablers)
**Depends on:** F1.1, F2.1 · **Blocks:** lawful operation in launch markets

## Why
We're a **processor** for recipients' data and **controller** for tenant-users; we must offer a DPA,
capture consent, and respect data residency (CBN flows via fintech customers).
(`COMPLIANCE-AND-DATA-PROTECTION.md`.)

## Stories
- **US-7.6.1** — As a **tenant**, a DPA is in place when I sign up, so my use is contractually compliant.
- **US-7.6.2** — As a **compliance officer**, each tenant has a `data_region`, so data is handled per local law.
- **US-7.6.3** — As a **prospect**, I see a clear privacy notice and consent terms at signup.

## Acceptance criteria
- [ ] **DPA template** auto-incorporated into ToS at signup (processor terms + sub-processor reference).
- [ ] **Privacy notice + consent** presented and recorded at onboarding.
- [ ] **`data_region`** attribute on tenants (and on integration instances) drives storage/processing region.
- [ ] Cross-border transfer requires an adequacy/safeguard flag.
- [ ] Test: signup records DPA acceptance + consent; `data_region` set and enforced on storage.

## Enablers (non-code, tracked)
- [ ] **Ghana DPC data-controller registration** (criminal if unregistered) before processing.
- [ ] Appoint a **DPO / Data Protection Supervisor**.
- [ ] Choose the **launch hosting region** (NDPA/CBN-aligned).

## Out of scope (this PI)
- RoPA tooling; certifications (ISO/SOC); per-country rule engine.

## Definition of Done
- Signup captures DPA+consent; `data_region` enforced; enablers tracked to completion.
