# F7.5 — DLR-trust probing

**Epic:** E7 Compliance · **Priority:** MUST (basic) · **Iteration:** 4 · ★ our wedge
**Depends on:** F5.4 · **Blocks:** F9.5 (trust view), routing (PI-2)

## Why
The market's #1 problem is **fake DLRs** — routes reporting `delivered` for messages they dropped.
You can't detect it from the DLR stream alone; you need independent probing. This is our
reliability differentiator, so it's P1, not an afterthought.

## Stories
- **US-7.5.1** — As an **operator**, I can see each route's *real* delivery rate vs its *reported* DLRs, so I can spot routes faking delivery.
- **US-7.5.2** — As the **platform**, I periodically send probe messages to known test numbers and compare actual receipt to the DLR, so trust scoring is evidence-based.

## Acceptance criteria
- [ ] Scheduled **probe sends** to controlled test numbers/SIMs per route/provider.
- [ ] Compare **actual receipt** (confirmed at the test endpoint) to the **reported DLR**; record divergence.
- [ ] Maintain a per-route **DLR-trust score**; surface in the operator health view (F9.5).
- [ ] Alert when a route's reported-delivered materially exceeds confirmed delivery.
- [ ] Test: a simulated route that reports `delivered` but the probe never arrives lowers the trust score + alerts.

## Design notes
- PI-1 = monitoring/visibility + alerting. **Trust-weighted routing decisions = PI-2** (needs the failover engine).
- Pairs with the "delivered, not sent" positioning wedge.

## Out of scope (this PI)
- Auto-rerouting away from low-trust routes; third-party monitoring integration.

## Definition of Done
- Probe→compare→score pipeline; divergence alert test.
