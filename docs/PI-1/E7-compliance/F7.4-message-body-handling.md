# F7.4 — Message-body handling (store / encrypt / retain / redact)

**Epic:** E7 Compliance · **Priority:** MUST · **Iteration:** 3
**Depends on:** F7.1 · **Blocks:** F6.2

## Why
Bodies are useful for support/troubleshooting but are sensitive PII. Match the market: store by
default, encrypted, time-bound, with opt-out (Twilio/Plivo/Bird).

## Stories
- **US-7.4.1** — As a **tenant**, I can choose whether message bodies are stored, so I can meet my own privacy posture.
- **US-7.4.2** — As a **compliance officer**, stored bodies are encrypted and purged after a retention window, so we minimize exposure.

## Acceptance criteria
- [ ] Body stored **by default**, in the encrypted **`pii_vault`** (F7.1); `messages.body_ref` references it (nullable).
- [ ] **Account-level opt-out** (`store_message_bodies=false`) → body never written.
- [ ] **Per-message `redact=true`** → no vault body entry (OTP always redacted, F6.2).
- [ ] **Retention purge** job deletes the vault body + nulls `body_ref` after `retain_until` (default ~180d, configurable); message metadata retained.
- [ ] Test: opt-out writes no body; redact flag honored; purge nulls bodies past retention while keeping metadata.

## Design notes
- Retention default authored via control-plane settings; purge respects the configured window.

## Out of scope (this PI)
- Per-country retention rule variation (later rule engine).

## Definition of Done
- Opt-out/redact/purge tests; metadata survives purge.
