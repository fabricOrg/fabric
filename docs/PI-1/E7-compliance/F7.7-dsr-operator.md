# F7.7 — DSR (operator-initiated access / erasure)

**Epic:** E7 Compliance · **Priority:** MUST (basic) · **Iteration:** 3–5
**Depends on:** F7.1, F1.4, F2.2 · **Blocks:** —

## Why
We must be able to fulfill data-subject requests (access, erasure). PI-1 ships an **operator-driven**
path; self-serve DSR-by-API (Bird-style) is PI-2.

## Stories
- **US-7.7.1** — As a **compliance officer/operator**, I can fulfill an access request for a phone number, exporting that subject's data, so we honor access rights.
- **US-7.7.2** — As a **compliance officer/operator**, I can erase a subject's PII (crypto-shred) while retaining financial/audit records, so we honor erasure lawfully.

## Acceptance criteria
- [ ] Operator action (in admin console) to **look up a subject by phone** (tenant-scoped) and **export** their data (access).
- [ ] Operator action to **erase** a subject → triggers DEK destruction (F7.1); ledger/audit retained.
- [ ] Both actions require **step-up auth** (F2.2) and are **audited** (F1.4); an `erasure_log` proof is kept.
- [ ] As processor, requests are executed **only within the requesting tenant's** data.
- [ ] Test: access export returns the subject's records; erasure renders PII unreadable + writes proof; cross-tenant access denied.

## Design notes
- **DSR-by-API (async → webhook), Bird's Personal Data API pattern = PI-2.**

## Out of scope (this PI)
- Self-serve DSR API; automated rectification/portability flows.

## Definition of Done
- Operator access + erasure flows tested; audit + erasure_log written; tenant-scoping enforced.
