# F7.3 — Sender-ID registration workflow

**Epic:** E7 Compliance · **Priority:** MUST · **Iteration:** 3
**Depends on:** F5.1, F9.3 · **Blocks:** F5.2 (send gating)

## Why
Unregistered/generic sender IDs get filtered or blocked by African MNOs. A registered, approved
sender ID is the price of deliverability — and approval is a multi-day, per-operator process.

## Stories
- **US-7.3.1** — As a **tenant**, I can register a sender ID and track its approval per country, so I know when I can use it.
- **US-7.3.2** — As the **platform**, sends with an unapproved sender ID are blocked, so we don't burn traffic on filtered routes.
- **US-7.3.3** — As an **operator**, I can review and approve/reject sender-ID requests (F9.3).

## Acceptance criteria
- [ ] `sender_ids` are tenant-owned with **per-country / per-operator approval state** (`pending | approved | rejected`).
- [ ] Format validation (e.g. ≤11 chars, allowed charset); supporting docs captured.
- [ ] A send with an **unapproved** sender ID for the destination country is **rejected** with a clear error (before reserve).
- [ ] Approval workflow surfaces in the operator queue (F9.3); state changes audited.
- [ ] Test: send blocked on unapproved ID; allowed once approved for that country.

## Design notes
- Sender ID = brand identifier, **not** recipient PII (no tokenization needed).
- Multi-day approval tracked as workflow state; operator-driven in PI-1.

## Out of scope (this PI)
- Automated operator/MNO submission APIs; per-country paperwork automation.
- **Surface note:** PI-1 has no business dashboard — tenants submit sender-ID requests via the **public API + dev portal**; the self-serve submission UI lands with the dashboard in PI-2. (Operator review UI = F9.3.)

## Definition of Done
- Approval-state gating test; operator approve/reject updates state + audit.
