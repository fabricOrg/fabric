# F7.1 — PII tokenization (vault + crypto-shred)

**Epic:** E7 Compliance · **Priority:** MUST · **Iteration:** 1 · ★ schema-shaping, build first
**Depends on:** F1.1 · **Blocks:** F5.2, F5.4, F3.1 refs, F7.7

## Why
Raw personal data (phone, body) must be isolated so right-to-erasure works against an immutable
ledger/audit. Resolution = tokenize + crypto-shred. (`COMPLIANCE-AND-DATA-PROTECTION.md §5`; Bird pattern.)

## Stories
- **US-7.1.1** — As a **compliance officer**, I can erase a person's PII on request while financial/audit records stay intact, so we honor erasure and accounting law simultaneously.
- **US-7.1.2** — As the **platform**, no table stores a raw phone number or body except the encrypted vault, so PII exposure is contained to one place.

## Acceptance criteria
- [ ] `data_subjects(subject_id, tenant_id)` surrogate; **`pii_vault`** holds phone/body/attributes **encrypted with a per-subject DEK**.
- [ ] `messages`, `contacts`, `otp_requests`, ledger refs use **`subject_id`** — **never** a raw PII column (lint/test enforced).
- [ ] **Erasure = destroy the subject's DEK** → PII permanently unreadable in one op; ledger/audit rows remain.
- [ ] An `erasure_log` records the request + completion (retained as compliance proof).
- [ ] **Envelope encryption:** per-subject DEKs are wrapped by a master key in **KMS**; only wrapped DEKs are stored. Erasure destroys the (wrapped) DEK.
- [ ] **Hot-path performance:** unwrapped DEKs are **cached in-memory (short TTL)** so per-message PII read/write doesn't make a KMS call each time.
- [ ] **Cluster-wide cache invalidation on erasure (B7):** erasure publishes a **Redis pub/sub** invalidation so *all* nodes evict the DEK — not just a per-node TTL expiry (which would leave the subject readable on other nodes until TTL). The bounded residual window (pub/sub propagation) is documented as accepted risk.
- [ ] **Erasure vs in-flight send (B7):** erasure is **blocked/deferred while the subject has any non-terminal message** (reserved/queued/sending). If a DEK is nonetheless destroyed before a worker can resolve the recipient, the send **terminates as `failed` with a compliance error code and the reservation is refunded** — never charged, never a stuck reservation. (Pick: block-while-non-terminal is primary; fail+refund is the backstop.)
- [ ] **KMS-unavailable behavior is defined:** new PII writes/sends **fail closed** (don't silently store unencrypted); reads degrade gracefully (cached or error, never plaintext fallback).
- [ ] **Master-key rotation** supported without re-shredding subjects (re-wrap DEKs); rotation is audited.
- [ ] Test: no raw PII column exists in business tables; post-erasure vault data is unreadable while ledger entries remain valid; KMS-down path fails closed; **erasure during an in-flight send → send fails + refunds, no stuck reservation**; **cluster cache invalidation evicts on all nodes**.

## Design notes
- Crypto-shredding via per-subject DEK + envelope encryption (KMS master key); resolve PII through the vault on read.
- **Must land in the first migrations** — retrofitting tokenization later is a brutal migration.
- DEK-cache TTL balances latency vs blast radius; coordinate with the o11y/no-PII-in-logs rule (F1.5).

## Out of scope (this PI)
- DSR self-serve API (operator-initiated only in PI-1, F7.7).

## Definition of Done
- No-raw-PII lint/test; erasure-renders-unreadable test; ledger integrity post-erasure.
