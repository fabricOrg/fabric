# F8.3 — Error model + request IDs

**Epic:** E8 DX · **Priority:** MUST · **Iteration:** 5
**Depends on:** — · **Blocks:** all endpoints

## Why
A typed, consistent error envelope + a request ID on every response makes errors programmatically
handleable and turns support into "give me the `req_` id."

## Stories
- **US-8.3.1** — As a **developer**, errors come back in a consistent, typed shape with a field pointer, so I can handle them in code.
- **US-8.3.2** — As a **developer/support**, every response carries a request ID, so issues are traceable.

## Acceptance criteria
- [ ] Error envelope: `{ error: { type, code, message, param?, doc_url? } }`; `type ∈ {api_error, auth_error, invalid_request_error, idempotency_error, rate_limit_error, …}`.
- [ ] Semantic HTTP codes: 400/401/402/403/404/409/422/429/5xx used correctly (402 = insufficient funds).
- [ ] Every response (success + error) includes a **`request_id`** (`req_…`), also logged + traceable (F1.5).
- [ ] `param` pinpoints the offending field on validation errors; `message` is user-safe.
- [ ] Test: validation error returns `param`; insufficient funds returns 402; request_id present on all responses.

## Design notes
- Mirrors Stripe's envelope + Twilio's stable numeric codes via `code`.

## Out of scope (this PI)
- Public error-code dictionary site (docs fast-follow).

## Definition of Done
- Error-shape + HTTP-code + request-id tests across representative endpoints.
