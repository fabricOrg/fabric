# F8.2 — Idempotency-Key (public API)

**Epic:** E8 DX · **Priority:** MUST · **Iteration:** 5
**Depends on:** F1.3 · **Blocks:** safe send/top-up retries

## Why
The public surface of F1.3 — Stripe's exact, trusted semantics so developers can retry safely.

## Stories
- **US-8.2.1** — As a **developer**, I send an `Idempotency-Key` on writes and can safely retry on timeout without double-charging or double-sending.

## Acceptance criteria
- [ ] All mutating POSTs honor an **`Idempotency-Key`** header.
- [ ] First response cached and **replayed for 24h** — replay **2xx/4xx but not 5xx/transient** (so a retry after a transient fault re-executes — N1).
- [ ] A replayed response carries **`Idempotent-Replayed: true`**.
- [ ] Same key + **different request fingerprint** → `idempotency_error`. Fingerprint per **F1.3 (B5)** — `SHA-256(method+path+canonical raw body)` computed at the edge before tokenization, so a byte-identical retry never falsely conflicts.
- [ ] Same key while the first request is **in-flight** → handled (locked) without double-execution.
- [ ] Test: replay (2xx + 4xx), **5xx not cached**, conflict on changed body, **byte-identical retry does not conflict**, in-flight concurrency.

## Design notes
- Backed by F1.3; applies to `sms/send`, `verify`, `wallet/topups`, etc.

## Out of scope (this PI)
- Server-generated keys (clients must supply).

## Definition of Done
- Replay/conflict/in-flight tests; `Idempotent-Replayed` header verified.
