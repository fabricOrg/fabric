# F8.1 — API versioning

**Epic:** E8 DX · **Priority:** MUST · **Iteration:** 5
**Depends on:** F2.3 · **Blocks:** all public endpoints

## Why
Ship breaking changes without breaking integrators — the Stripe reputation. Decide the scheme once,
at v1, before external traffic exists.

## Stories
- **US-8.1.1** — As a **developer**, my integration keeps working when the platform evolves, so upgrades are opt-in.

## Acceptance criteria
- [ ] A versioning scheme is fixed at launch: **date-based, account-pinned**, overridable per-request via a **`Version` header** (path `/v1` namespace for the major line).
- [ ] An account stays pinned to its version until it explicitly upgrades.
- [ ] Version is recorded on requests for support/debugging.
- [ ] Test: a request without a `Version` header uses the account's pinned version; an explicit header overrides.

## Design notes
- Stripe = date-based; Twilio = path-based. We adopt date-based + `Version` header for forward flexibility.

## Out of scope (this PI)
- Automated version-migration tooling; deprecation dashboards.

## Definition of Done
- Pinning + header-override tests; version recorded on requests.
