# F8.5 — Test mode + magic numbers

**Epic:** E8 DX · **Priority:** MUST · **Iteration:** 5
**Depends on:** F2.3, F5.1 (FakeProvider) · **Blocks:** developer onboarding

## Why
Developers must build and test every success *and* failure branch before real spend — the core of
fast self-serve onboarding (Stripe magic cards / Twilio magic numbers).

## Stories
- **US-8.5.1** — As a **developer**, `sk_test_` keys let me exercise the full API without charges or real delivery.
- **US-8.5.2** — As a **developer**, magic recipient numbers deterministically simulate outcomes (delivered/failed/etc.) so I can test my webhook handling in CI.

## Acceptance criteria
- [ ] `sk_test_` keys (F2.3) route to **test mode**: validate exactly like live, **never charge, never hit a real carrier**, separate test data.
- [ ] **Magic MSISDNs** deterministically yield `delivered | undelivered | failed | rejected | insufficient_funds` via the FakeProvider (F5.1).
- [ ] **Unlike Twilio, test mode FIRES status callbacks/webhooks**, so DLR handling is testable.
- [ ] Test wallet can be funded with test credit (no real payment).
- [ ] Test: each magic number produces its outcome + corresponding webhook; no real charge/send occurs.

## Design notes
- Documented magic-number table published in dev docs (F8.6).

## Out of scope (this PI)
- Record/replay of live traffic into test.

## Definition of Done
- Magic-number outcome + callback tests; test-mode isolation (no real spend/send) verified.
