# F8.4 — Outbound webhooks

**Epic:** E8 DX · **Priority:** MUST (core) · **Iteration:** 5
**Depends on:** F1.2 · **Blocks:** developer event consumption

## Why
Developers need reliable, verifiable event delivery (message status, top-ups). Beat Twilio's weak
single-retry; adopt Stripe-grade signing + retries.

## Stories
- **US-8.4.1** — As a **developer**, I register endpoints and receive signed events I can verify, so I can trust their authenticity.
- **US-8.4.2** — As a **developer**, transient failures are retried with backoff, so I don't lose events during a blip.

## Acceptance criteria
- [ ] Tenants register endpoints + subscribe to event types; each endpoint has its **own signing secret**.
- [ ] Signature = **`t=<unix>,v1=<HMAC-SHA256>`** over `"{t}.{body}"`; consumers enforce a **~5-min tolerance** (replay protection).
- [ ] **Exponential backoff retries over hours/days**; permanent failures → **dead-letter** for inspection.
- [ ] At-least-once delivery; events carry a stable `id` **and a per‑message monotonic `sequence`** so tenants can dedupe *and* order (handles cross-aggregate reordering, e.g. `delivered` arriving before `sent`) — S6.
- [ ] Driven by the outbox (F1.2); delivery attempts recorded. **Billing commit/refund is never driven *only* by an at-least-once event** — it goes through the B6 terminal guard (F5.4), so a duplicated event can't double-charge.
- [ ] **SSRF protection:** registered endpoint URLs must be **HTTPS, public** — internal/loopback/link-local/metadata addresses are rejected at registration and re-validated at delivery (DNS-rebind safe).
- [ ] Test: signature verify, tolerance rejection, retry/backoff, DLQ on permanent failure, and **rejection of an internal/metadata URL**.

## Design notes
- Per-endpoint secret (not the account key, unlike Twilio).
- **Manual replay UI + CLI listener = PI-2.**

## Out of scope (this PI)
- Replay UI; local-dev CLI tunnel.

## Definition of Done
- Signing/tolerance/retry/DLQ tests; at-least-once with dedupe verified.
