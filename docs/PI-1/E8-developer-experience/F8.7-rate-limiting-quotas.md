# F8.7 — Rate limiting & quotas

**Epic:** E8 DX · **Priority:** MUST · **Iteration:** 5 (edge; can start earlier)
**Depends on:** F2.3, F8.3 · **Blocks:** safe public exposure

## Why
A public API needs abuse and fair-use protection from day one — runaway loops, scraping, and
fraud must be contained without taking down the platform. Promised in `ARCHITECTURE.md §9` but not
yet storied.

## Stories
- **US-8.7.1** — As the **platform**, requests are rate-limited per API key and per tenant, so one caller can't degrade service for others.
- **US-8.7.2** — As a **developer**, when I exceed a limit I get a clear `429` with retry guidance, so I can back off correctly.

## Acceptance criteria
- [ ] **Per-API-key and per-tenant** rate limits (Redis token bucket), with sensible defaults + per-plan/per-tenant overrides (config, F9.1).
- [ ] **Atomic bucket (S7):** the token bucket is a single **atomic Redis Lua script** (or `CL.THROTTLE`/`redis-cell`) — never read-modify-write — so concurrent bursts cannot bypass the limit. The same atomic primitive backs the SMS-pumping/fraud controls (F6.3).
- [ ] Exceeding a limit returns **HTTP 429** with `rate_limit_error` (F8.3) and `Retry-After` + rate-limit headers (limit/remaining/reset).
- [ ] Limits apply to live traffic; **test mode** has its own (looser) limits.
- [ ] Send-specific throughput is bounded to protect the provider/queue (coordinates with bulk fan-out, F5.6).
- [ ] Test: burst beyond limit returns 429 + headers; limits are isolated per tenant.

## Design notes
- Edge concern; defaults authored in the control plane (F9.1).
- Distinct from F6.3 (fraud/pumping) — this is generic fair-use throttling.

## Out of scope (this PI)
- Dynamic/adaptive limits; per-endpoint cost weighting (PI-2).

## Definition of Done
- 429 + headers test; per-tenant isolation test; config-driven override verified.
