# F1.6 — Platform notifications (transactional)

**Epic:** E1 Foundations · **Priority:** MUST (basic) · **Iteration:** 2
**Depends on:** F1.2 · **Blocks:** F3.7 low-balance, F9.3 sender-ID, F4.2 receipts

## Why
Several PI-1 features need to *notify the tenant* (low balance, sender-ID approved/rejected, top-up
receipt) but there's no notification channel. This provides the minimal transactional one.

## Stories
- **US-1.6.1** — As a **tenant**, I receive transactional notices (low balance, sender-ID decision, top-up receipt) by email, so I'm informed without checking the dashboard.
- **US-1.6.2** — As the **platform**, notifications are event-driven and templated, so any feature can emit one consistently.

## Acceptance criteria
- [ ] A notification service consumes domain events (F1.2) and sends **transactional email** (provider-backed, e.g. an email API) to the tenant's users.
- [ ] Templated notices for: **low balance** (F3.7), **sender-ID approved/rejected** (F9.3/F7.3), **top-up succeeded** (F4.2).
- [ ] Delivery is **idempotent** (one event → one notice) and recorded; failures retried.
- [ ] Per-tenant notification preferences (at least on/off per category).
- [ ] Test: each triggering event produces exactly one notice; opt-out suppresses it.

## Design notes
- Auth/verification emails are handled by WorkOS; this covers *platform* notices.
- Channel = email in PI-1; in-app + SMS-to-self + richer prefs = later.

## Out of scope (this PI)
- In-app notification center; SMS/WhatsApp notification channels; digest scheduling.

## Definition of Done
- Event→notice idempotency test; the three PI-1 notice types fire; preference opt-out honored.
