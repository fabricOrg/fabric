# F1.3 — Idempotency service (internal)

**Epic:** E1 Foundations · **Priority:** MUST · **Iteration:** 1
**Depends on:** F1.1 · **Blocks:** F3.2 debit, F4.2 top-up, F8.2 public idempotency

## Why
A reusable mechanism so any money/PII-affecting operation can be made safely retryable. F8.2 is the
public HTTP surface; this is the engine underneath.

## Stories
- **US-1.3.1** — As the **platform**, a repeated operation with the same idempotency key produces the original result exactly once, so retries (client or webhook) never double-charge or double-send.

## Acceptance criteria
- [ ] Store keyed by `(tenant_id, idempotency_key)` with a **unique constraint**.
- [ ] First call records `status` (in_progress → done) + a **response snapshot** (status code + body).
- [ ] A concurrent second call with the same key while the first is in-flight is **serialized** (locked) and does not double-execute.
- [ ] A repeat after completion **replays** the stored response. **Replay 2xx and 4xx; do NOT cache 5xx/transient** (so a retry after a transient fault re-executes rather than pinning a stale error — N1).
- [ ] Keys **expire after 24h**; same key after expiry = a fresh operation.
- [ ] **Fingerprint spec (B5):** the fingerprint = `SHA-256(method + path + canonicalized raw request body)`, computed **at the edge before any PII tokenization or server enrichment** (so a legitimate byte-identical retry never conflicts, and the body's later `subject_id` substitution doesn't affect it). Volatile/server-added fields and auth headers are excluded. Same key + **different fingerprint** → `idempotency_error` conflict.

## Design notes
- Mirrors Stripe semantics (24h, replay-even-errors-except-transient). Durable in Postgres; hot path may front with Redis.
- Fingerprint operates on **raw inbound bytes**, never post-tokenization state — critical because the SMS body is tokenized into `pii_vault` downstream (B5).
- Used by the wallet (F3.2), top-up confirm (F4.2), and exposed via the API (F8.2).

## Out of scope (this PI)
- Cross-region key replication.

## Definition of Done
- Concurrency test (two simultaneous same-key calls → one execution); replay-after-done test; conflict test.
