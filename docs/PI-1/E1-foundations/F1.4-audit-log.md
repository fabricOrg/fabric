# F1.4 — Immutable audit log

**Epic:** E1 Foundations · **Priority:** MUST · **Iteration:** 1
**Depends on:** F1.2 · **Blocks:** F9.4 maker-checker, F7.7 DSR, compliance

## Why
Every money movement and every privileged/control-plane action must be reconstructable — for
forensics, support ("why did all sends fail at 14:00?"), and compliance evidence. (`CONTROL-PLANE-ADMIN.md §8`.)

## Stories
- **US-1.4.1** — As a **compliance officer**, I can see an immutable record of who did what, when, and why, so I can demonstrate accountability and investigate incidents.
- **US-1.4.2** — As an **operator**, every privileged action I take is logged with before/after state, so changes are traceable.

## Acceptance criteria
- [ ] `audit_log` is **append-only** (no UPDATE/DELETE; enforced at DB privilege level).
- [ ] Each entry: `actor_type[staff|system]`, `actor_id`, `action`, `target_type/id`, `before`, `after`, `reason`, `ip`, `request_id`, `created_at`.
- [ ] All money movements and all control-plane config/ops actions write an entry.
- [ ] Entries are queryable by tenant, actor, target, and time range.
- [ ] Test: attempting to UPDATE/DELETE an audit row fails.

## Design notes
- Tamper-evident (append-only + restricted grants); fed partly via the outbox (F1.2).
- Distinct from domain events — audit is the durable governance record.

## Out of scope (this PI)
- Cryptographic hash-chaining / external WORM storage (consider later).

## Definition of Done
- Immutability test; coverage check that money + config actions emit audit entries.
