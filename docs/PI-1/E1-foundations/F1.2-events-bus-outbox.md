# F1.2 — Events-bus (transactional outbox)

**Epic:** E1 Foundations · **Priority:** MUST · **Iteration:** 1
**Depends on:** F1.1 · **Blocks:** F1.4 audit, F8.4 webhooks, all domain events

## Why
Domain events (message.sent, topup.succeeded, …) must be emitted **atomically** with the state
change that produced them — otherwise we get lost events or phantom side-effects on the money path.

## Stories
- **US-1.2.1** — As the **platform**, when a state change commits, its domain event is guaranteed to be published exactly once, so downstream consumers (webhooks, monitoring) never miss or duplicate-trigger.
- **US-1.2.2** — As a **developer** building a consumer, I receive events with a stable ID so I can dedupe.

## Acceptance criteria
- [ ] Events are written to an **`outbox_events`** table **in the same DB transaction** as the state change.
- [ ] A relay polls/streams the outbox and publishes; `published_at` marks completion; unpublished rows are retried.
- [ ] Each event has a stable unique `id`, `type`, `tenant_id`, `aggregate_type/id`, `payload`, `occurred_at`.
- [ ] Delivery is **at-least-once**; consumers dedupe on event `id`.
- [ ] Test: a transaction that rolls back leaves **no** published event; a committed change always yields exactly one relayed event.

## Design notes
- Transactional-outbox pattern; relay is idempotent and ordered per aggregate where it matters.
- This bus feeds F1.4 (audit), F8.4 (tenant webhooks), and control-plane monitoring (consume-only).

## Out of scope (this PI)
- External message broker (Kafka/etc.) — in-process relay is sufficient for PI-1.

## Definition of Done
- Rollback-leaves-no-event test; at-least-once relay test with forced consumer failure + retry.
