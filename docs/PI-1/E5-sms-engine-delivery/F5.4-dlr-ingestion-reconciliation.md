# F5.4 — DLR ingestion + reconciliation

**Epic:** E5 SMS · **Priority:** MUST · **Iteration:** 3
**Depends on:** F5.3, F3.2, F3.5 · **Blocks:** correct billing, F7.5

## Why
The DLR is the asynchronous truth about delivery. It finalizes billing (commit/refund) and feeds the
"honest delivery" wedge — and must be robust to out-of-order, duplicate, and missing callbacks.

## Stories
- **US-5.4.1** — As the **platform**, when a provider DLR arrives I map it to canonical status, finalize the charge, and update the message — exactly once.
- **US-5.4.2** — As a **tenant**, my message status reflects the *real* delivery outcome, not a phantom "sent".

## Acceptance criteria
- [ ] DLR webhook received via `webhooks-ingress` with **signature verification** per provider.
- [ ] **DLR dedupe (B6/S8):** each DLR is persisted with `UNIQUE(provider_instance_id, provider_message_ref, canonical_status)` (or the provider's DLR id if supplied). Reconciliation is driven off the **first successful insert**; a duplicate insert conflicts and is a no-op.
- [ ] **Shared resolution state machine (B6):** the message/reservation row carries a billing-resolution state `reserved → committed | refunded` (terminal). The DLR handler takes `SELECT … FOR UPDATE` on that row and applies a **compare-and-set**: it transitions only if current state is `reserved`. The reservation sweeper (F3.3) uses the *same* lock + guard, so DLR and sweeper can never both resolve.
- [ ] Raw status → canonical (F5.3); message status updates are **monotonic** (a later lower/out-of-order status never overwrites a terminal one).
- [ ] Reconciliation drives F3.2 outcome: **commit** on a billable status (F3.5), **refund** on platform-fault/non-billable.
- [ ] **Late-after-sweep policy (S4):** if a refund already resolved the row, a later authoritative `delivered` DLR does **not** flip it (PI-1 accepts the rare revenue loss); the event is logged for DLR-trust (F7.5). *(Decision recorded here so the state machine stays simple: terminal is terminal.)*
- [ ] Emits `message.delivered` / `message.undelivered` (F1.2) → tenant webhooks (F8.4), carrying event `id` + per-message sequence (S6).
- [ ] Test: duplicate DLR, out-of-order DLR, **concurrent DLR + sweeper** (exactly one resolution), late-after-sweep, signature-invalid.

## Design notes
- Persist a `delivery_reports` log (raw + canonical) for audit and DLR-trust scoring (F7.5).
- The resolution state machine + `FOR UPDATE` is the single guard that makes B6 (DLR-vs-sweeper) and B2 (retry) safe; it lives on the message row and is owned jointly by this story, F5.2, and F3.3.
- **Segment reconciliation (S3):** if the first provider's DLR does **not** carry actual segment count, the reserved estimate *is* the charge (no adjustment) — confirmed for the launch provider; the "adjust on actual segments" path is dropped from PI-1.

## Out of scope (this PI)
- Carrier-specific deep error analytics.

## Definition of Done
- Idempotent reconciliation tests; billing finalization verified against F3.5 table.
